# 运行用例分析

本文用于验收讲解。由于程序是多线程并发运行，日志的精确先后顺序每次可能略有不同；验收时重点看同步关系是否成立，而不是逐行背诵固定输出。

## 1. 快速验证运行

命令：

```bash
make -C OS/library_cache_sync run-quick
```

参数含义：

```text
readers=3, writers=1, cache-size=2, rounds=2
delay-min-ms=1, delay-max-ms=3, seed=42
```

这个用例延时很短，适合先快速确认程序能运行、能退出、关键流程都有日志。缓存大小只有 2，读者请求的书多于缓存容量时，容易观察到缓存 miss、缓存加载、缓存命中和 LRU 替换。

验收观察点：

1. 读者并发进入读区：

```text
Reader-01 enter read section active_readers=1 first_reader_locked_db
Reader-02 enter read section active_readers=2
Reader-03 enter read section active_readers=3
```

可以说明第一个读者通过 `db_sem` 阻止写者，后续读者只增加 `read_count`，因此多个读者可以并发读取。

2. 缓存 miss 后提交加载请求：

```text
cache miss book=Algorithm enqueue request_id=1
CacheManager load begin book=Algorithm reader=1 request_id=1
```

可以说明读者不直接访问主数据库，而是把 `{reader_id, book_name, request_id}` 放入请求队列，由缓存管理器后台加载。

3. 加载完成后读者再读取：

```text
loaded into free slot book=Algorithm version=1 cache=[Algorithm:v1:pin1]
Reader-01 read after load book=Algorithm version=1
```

可以说明缓存管理器加载后会 pin 住缓存项并唤醒对应读者，读者复制完成后释放 pin，避免刚加载的数据被淘汰。

4. 缓存命中直接读取：

```text
cache hit book=Algorithm version=1
```

可以说明同一本书已经在缓存中时，读者不需要再次触发加载，直接读取缓存副本。

5. 缓存满时 LRU 替换：

```text
replaced LRU slot book=Compiler version=1
```

可以说明缓存容量真实受限，满了以后只替换未被 pin 的最近最少使用项。

6. 写者等待读者退出后才写：

```text
Writer-01 wait write book=Linux
Reader-xx leave read section active_readers=0 last_reader_released_db
Writer-01 update database begin book=Linux
```

可以说明写者必须等最后一个读者释放 `db_sem` 后才能更新数据库，满足写者独占。

7. 程序正常结束：

```text
CacheManager shutdown received
CacheManager exit
Main finished
```

可以说明主线程等待读者和写者结束后，发送 `Shutdown` 请求唤醒缓存管理器退出，没有死锁。

## 2. 验收演示运行

命令：

```bash
make -C OS/library_cache_sync run-demo
```

参数含义：

```text
readers=8, writers=3, cache-size=5, rounds=5
delay=默认 1000 到 5000 毫秒
```

这个用例更接近题目要求：8 个读者、3 个写者，每个线程执行 5 轮，并使用 1 到 5 秒随机延时。运行时间较长，但日志更容易展示真实并发交错。

验收观察点：

1. 多个读者并发：

观察 `active_readers` 是否经常大于 1。只要出现多个读者同时处于读区，就能证明读者共享读取成立。

2. 写者独占：

观察某个写者进入：

```text
Writer-xx update database begin book=...
Writer-xx update database done book=...
Writer-xx leave write book=...
```

在写者持有 `db_sem` 的这段期间，不应出现新的读者进入读区，也不应出现另一个写者同时 `update database begin`。

3. 写后缓存刷新：

如果写者更新的书在缓存中，会出现：

```text
refresh cache begin book=... version=...
refresh cache done book=... version=...
```

可以说明写者更新主数据库后，会在释放写锁前同步刷新缓存副本，保证后续读者不会读到旧版本。

4. 写后无缓存副本时跳过刷新：

```text
cache has no copy book=..., skip refresh
```

可以说明系统只刷新已有缓存副本，不把所有写入都强制插入缓存，保持缓存“最近访问副本池”的语义。

5. 版本号递增：

```text
update database done book=Linux version=2
update database done book=Linux version=3
```

可以说明主数据库真实维护版本号，写者每次更新都会递增版本；如果缓存中有对应副本，刷新后的缓存版本应与数据库版本一致。

验收讲法：

这个用例用于综合演示题目一完整功能。读者数量和写者数量符合题目建议配置，随机延时让线程交错更明显，可以观察到读者优先、写者独占、缓存加载、缓存刷新和正常退出。

## 3. 缓存容量为 1 的边界用例

命令：

```bash
make -C OS/library_cache_sync run-cache-one
```

参数含义：

```text
readers=3, writers=0, cache-size=1, rounds=2
delay-min-ms=1, delay-max-ms=2, seed=42
```

这个用例没有写者，只测试读者和缓存管理器。缓存容量只有 1，任何不同书籍的加载都会导致替换，适合验证有界缓存、LRU 替换和 pin 保护是否稳定。

验收观察点：

1. 缓存只能保存一本书：

日志里的缓存快照通常类似：

```text
cache=[Algorithm:v1]
cache=[Security:v1]
cache=[Compiler:v1]
```

可以说明缓存数组容量真实受限，没有越界保存多个条目。

2. 频繁替换但不死锁：

```text
replaced LRU slot book=Security version=1
replaced LRU slot book=Compiler version=1
```

可以说明缓存满时能持续替换未被保留的槽位，程序不会卡住。

3. pin 保护刚加载的数据：

```text
cache=[Security:v1:pin1]
Reader-xx read after load book=Security version=1
```

可以说明缓存管理器唤醒读者前会保留该缓存项，读者复制完成后释放保留，避免目标书还没被读者复制就被另一个请求淘汰。

4. 无写者场景正常退出：

```text
CacheManager shutdown received
Main finished
```

可以说明即使没有写者，读者和缓存管理器也能完成生产者-消费者流程并退出。

验收讲法：

这个用例主要证明缓存区是真正的有界缓冲区，不是简单 sleep 模拟。容量设置为 1 后，程序必须频繁执行真实的缓存插入和替换操作，同时通过 pin 标记避免并发淘汰错误。

## 4. 无读者、多写者边界用例

命令：

```bash
make -C OS/library_cache_sync run-writers-only
```

参数含义：

```text
readers=0, writers=2, cache-size=2, rounds=2
delay-min-ms=1, delay-max-ms=2, seed=9
```

这个用例没有读者，因此不会产生缓存加载请求，主要验证多个写者之间的互斥和缓存管理器的空队列退出逻辑。

验收观察点：

1. 写者逐个独占写入：

```text
Writer-01 update database begin book=...
Writer-01 update database done book=...
Writer-01 leave write book=...
Writer-02 update database begin book=...
```

可以说明两个写者都需要获取同一个 `db_sem`，因此不会同时进入写区。

2. 没有读者时不会产生缓存加载：

这个用例一般不会出现：

```text
CacheManager load begin
```

因为没有读者 miss，也就没有加载请求。缓存管理器启动后阻塞在 `request_count`，等待主线程最后发送 shutdown。

3. 写者更新但缓存无副本：

```text
cache has no copy book=..., skip refresh
```

可以说明没有读者加载缓存时，写者只更新主数据库；缓存中没有该书副本就不刷新。

4. 缓存管理器能被干净唤醒退出：

```text
CacheManager start
CacheManager shutdown received
CacheManager exit
```

可以说明主线程不会让后台线程永久阻塞，而是通过请求队列压入 `Shutdown` 请求结束缓存管理器。

验收讲法：

这个用例证明写者互斥逻辑独立成立。即使没有读者和缓存加载请求，程序也能正确处理写者串行写入，并让缓存管理器正常退出。

## 5. 汇总运行

命令：

```bash
make -C OS/library_cache_sync run-examples
```

该目标会按顺序执行：

```text
run-quick
run-demo
run-cache-one
run-writers-only
```

验收时如果时间充足，可以运行这个目标完整展示；如果时间有限，建议先运行 `run-quick`，再根据老师关注点补充运行 `run-cache-one` 或 `run-writers-only`。`run-demo` 使用默认 1 到 5 秒延时，完整运行时间较长，适合作为最终演示或报告截图来源。

## 6. 通用日志解释模板

可以按下面顺序讲：

1. `Main start`：说明本次线程数量、缓存大小和轮数。
2. `Reader request`：读者随机选择一本书。
3. `enter read section`：读者通过 `read_count + db_sem` 进入读者优先读区。
4. `cache hit`：缓存命中，直接复制缓存副本。
5. `cache miss`：缓存未命中，读者提交加载请求并等待。
6. `CacheManager load begin`：缓存管理器从请求队列取出请求。
7. `loaded into free slot` 或 `replaced LRU slot`：真实修改缓存数组。
8. `read after load`：读者被唤醒后再读取缓存副本。
9. `Writer update database begin/done`：写者独占更新主数据库。
10. `refresh cache begin/done`：写者同步刷新缓存副本。
11. `leave read section` 和 `leave write`：释放对应信号量。
12. `shutdown received` 和 `Main finished`：所有线程正常退出。

## 7. 常见追问回答

为什么日志顺序每次不完全一样？

因为 pthread 线程由操作系统调度，线程交错具有不确定性。程序保证的是同步约束不被破坏，例如写者不会和读者同时访问数据库，缓存结构操作受 `cache_mutex` 保护。

为什么有时写者先写，有时读者先读？

读者优先规则的含义是：只要已有读者处于读区，写者必须等待；但程序启动瞬间谁先获得 CPU 由系统调度决定。如果写者先拿到 `db_sem`，读者会等待写者完成。

为什么有时写者显示 `skip refresh`？

写者只刷新缓存中已经存在的副本。如果该书尚未被读者加载到缓存，缓存里没有副本，因此无需刷新。

为什么要有 `request_id`？

多个读者可能同时请求同一本书。`request_id` 可以让缓存管理器精确标记这次加载对应的缓存项，并唤醒正确读者，避免请求互相覆盖。

为什么要有 pin？

缓存满时会执行 LRU 替换。pin 用来保护刚加载、但读者尚未复制的缓存项，避免它被另一个加载请求立刻淘汰。
