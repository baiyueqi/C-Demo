## 第一题：共享数据库的并发访问控制（线程的同步/互斥）

### §1.1 第一题实验目标

本题以在线图书馆电子书数据库为场景，设计并实现一个共享数据库并发访问控制系统。系统中存在多个读者线程和写者线程：读者读取电子书，允许多个读者在没有写者写入时同时读取；写者更新电子书，写入期间必须独占数据库资源，禁止其他读者和写者访问。同时，系统引入固定容量的缓存区保存最近访问的电子书副本，读者读取前优先访问缓存，缓存未命中时由缓存管理器线程从主数据库加载到缓存；写者更新主数据库后，需要同步刷新缓存中已有的对应副本，保证缓存一致性。

本实验目标如下：

1. 掌握 POSIX 信号量的 P/V 操作，理解线程同步、互斥和临界区保护。
2. 使用 `pthread` 创建读者线程、写者线程和缓存管理器线程，模拟真实并发执行。
3. 实现读者优先和写者独占规则：多个读者可并发读取，写者写入时独占数据库。
4. 实现真实有界缓存区，包括缓存命中、缓存未命中、空槽插入、LRU 替换和缓存刷新。
5. 使用生产者-消费者模型处理缓存加载请求，避免多个读者缓存 miss 时互相覆盖请求。
6. 通过带时间戳的日志验证读者并发、写者互斥、缓存加载、缓存替换、写后刷新和正常退出。

开发环境与工具如下：

线程库：pthread
同步机制：POSIX semaphore

### §1.2 第一题原理、方法、过程

#### 1.2.1 总体设计思想

系统将在线图书馆拆分为五个模块：主数据库模块、缓存区模块、请求队列模块、线程模拟模块和延时模块。

```text
读者线程
  -> 进入读区
  -> 查询缓存
  -> 命中则直接读取缓存副本
  -> 未命中则提交加载请求并等待缓存管理器
  -> 读取完成后离开读区

写者线程
  -> 等待数据库写锁
  -> 独占更新主数据库
  -> 如果缓存中有对应副本则刷新缓存
  -> 释放数据库写锁

缓存管理器线程
  -> 等待请求队列
  -> 从主数据库加载目标书籍
  -> 插入空槽或替换 LRU 缓存项
  -> 唤醒对应读者
```

主数据库真实保存电子书内容和版本号，写者每次更新都会使版本号递增。缓存区是真实的固定容量数组，每个槽位保存书籍副本、LRU 时间戳和 pin 保护标记。请求队列保存 `{reader_id, book_name, request_id}`，用于解决多个读者同时 miss 时的请求传递问题。

#### 1.2.2 关键数据结构

电子书结构如下：

```cpp
struct Book {
    std::string name;
    std::string content;
    int version;
};
```

`version` 用于观察写者更新后的数据变化。主数据库初始包含“操作系统、Linux基础、数据库系统、编译原理、计算机网络、信息安全、算法设计”等书籍。

缓存槽结构如下：

```cpp
struct CacheEntry {
    bool valid;
    Book book;
    unsigned long last_access_tick;
    std::set<int> pinned_request_ids;
};
```

其中 `valid` 表示槽位是否有效，`last_access_tick` 用于 LRU 替换，`pinned_request_ids` 用于保护刚由缓存管理器加载、但读者尚未复制完成的缓存项，避免目标书籍刚加载就被其他请求淘汰。

#### 1.2.3 信号量设计

核心信号量和共享变量如下：

| 名称 | 初值 | 作用 |
| --- | ---: | --- |
| `db_sem` | 1 | 数据库访问控制。第一个读者进入时 P，最后一个读者离开时 V；写者写入时独占 P/V |
| `read_mutex` | 1 | 保护 `read_count` |
| `read_count` | 0 | 当前正在读区内的读者数量 |
| `cache_mutex` | 1 | 互斥保护缓存数组 |
| `empty_slots` | N | 缓存空槽数量，首次插入缓存项时使用 |
| `full_slots` | 0 | 缓存已占用槽数量，用于体现有界缓存容量变化 |
| `cache_unpinned` | 0 | 缓存已满且所有槽位被保护时，缓存管理器等待读者释放 pin |
| `request_mutex` | 1 | 互斥保护加载请求队列 |
| `request_count` | 0 | 请求队列中待处理请求数，缓存管理器在此等待 |
| `reader_ready[i]` | 0 | 第 i 个读者的独立完成通知 |
| `log_mutex` | 1 | 串行化日志输出 |

本设计没有使用单个全局书名变量传递请求，而是使用请求队列。这样可以避免多个读者同时缓存未命中时覆盖同一个共享变量，也能让缓存管理器准确唤醒对应读者。

#### 1.2.4 读者优先原理

读者优先由 `read_count + db_sem` 实现。第一个读者进入读区时执行 `P(db_sem)`，阻止写者进入；后续读者只增加 `read_count`，因此多个读者可以同时读取。最后一个读者离开时执行 `V(db_sem)`，允许等待中的写者进入。

核心伪代码如下：

```text
enter_read():
    P(read_mutex)
    if read_count == 0:
        P(db_sem)
    read_count++
    V(read_mutex)

leave_read():
    P(read_mutex)
    read_count--
    if read_count == 0:
        V(db_sem)
    V(read_mutex)
```

该方法满足题目要求的“读者优先”：当已有读者正在读取时，写者必须等待；多个读者之间可以并发读取。

#### 1.2.5 写者独占原理

写者进入写区前执行 `P(db_sem)`，离开写区时执行 `V(db_sem)`。由于读者组也通过同一个 `db_sem` 阻塞写者，因此写者写入时不会有读者或其他写者同时访问数据库。

核心伪代码如下：

```text
writer():
    P(db_sem)
    update database
    if cache contains same book:
        update cache copy
    V(db_sem)
```

写者更新数据库后调用 `cache.updateIfPresent(updated)`，只刷新缓存中已有的副本；如果缓存中没有该书，则跳过刷新，保持缓存“最近访问副本池”的语义。

#### 1.2.6 缓存未命中和生产者-消费者模型

读者缓存未命中时不会直接访问主数据库，而是把请求压入请求队列：

```text
reader cache miss:
    push {reader_id, book_name, request_id} into request_queue
    V(request_count)
    P(reader_ready[reader_id])
    copy pinned cache item
    release pin
```

缓存管理器作为生产者，阻塞等待 `request_count`：

```text
cache_manager:
    P(request_count)
    pop request
    load book from database
    if target already in cache:
        update and pin
    else if free slot exists:
        insert into free slot and pin
    else:
        replace unpinned LRU slot and pin
    V(reader_ready[reader_id])
```

读者等待期间不持有 `cache_mutex`，缓存管理器加载时也不持有 `request_mutex`，避免长期操作占用互斥锁导致死锁。

#### 1.2.7 死锁避免设计

本项目采取以下措施避免死锁：

1. 不在持有 `cache_mutex` 时等待 `reader_ready`。
2. 不在持有 `request_mutex` 时执行数据库加载或延时操作。
3. 缓存已满但所有槽位被 pin 时，缓存管理器先释放 `cache_mutex`，再等待 `cache_unpinned`。
4. 写者锁顺序固定为 `db_sem -> cache_mutex`，读者进入读区后只短暂持有 `cache_mutex` 查询或复制缓存。
5. 主线程在读者和写者全部结束后压入 `Shutdown` 请求，唤醒缓存管理器正常退出。

### §1.4 第一题出现的错误及解决方法

1. 问题：最初如果用单个全局变量保存读者请求书名，多个读者同时缓存未命中时可能互相覆盖请求。
   解决方法：改用 `RequestQueue` 保存 `{reader_id, book_name, request_id}`，并用 `request_mutex` 保护队列，用 `request_count` 通知缓存管理器。

2. 问题：读者缓存 miss 后如果持有 `cache_mutex` 等待缓存管理器，会导致缓存管理器无法获得缓存锁，形成死锁。
   解决方法：读者发现 miss 后立即释放 `cache_mutex`，再提交请求并等待 `reader_ready`。

3. 问题：缓存管理器在缓存满且所有槽位都被读者 pin 保护时，如果一直持有 `cache_mutex` 等待，会阻塞读者释放 pin。
   解决方法：缓存管理器先释放 `cache_mutex`，再等待 `cache_unpinned`，被唤醒后重新尝试 LRU 替换。

4. 问题：缓存刚加载的书可能在读者复制前被其他请求替换，导致读者被唤醒后找不到目标副本。
   解决方法：为每个加载请求生成唯一 `request_id`，缓存管理器加载后给缓存项增加 pin，读者复制完成后释放 pin。

5. 问题：多线程日志同时输出时会互相穿插，难以观察真实同步关系。
   解决方法：增加 `log_mutex` 串行化日志输出，并在日志中加入毫秒级时间戳、线程名称、书名和版本号。

## 第二题：自定义 Linux 系统调用

### §2.1 第二题实验目标

第二题要求将第一题中用于模拟读、写、加载、刷新操作的随机延时函数改写为新的 Linux 系统调用，并在第一题主程序中使用。结合本项目实现，四类延时函数与系统调用对应关系如下：

```text
delay_read    -> diag_read(number)
delay_load    -> diag_load(number)
delay_write   -> diag_write(number)
delay_refresh -> diag_refresh(number)
```

每个系统调用接收学号 `number`，以学号和操作偏移作为随机种子，生成 1000 到 5000 毫秒之间的延时时间，并让当前进程睡眠。

本题实验目标如下：

1. 理解 Linux 系统调用从内核注册到用户态调用的完整路径。
2. 掌握在内核中使用 `SYSCALL_DEFINE1` 定义一个参数的系统调用。
3. 掌握在系统调用表中注册调用号，并在用户态通过 `syscall()` 调用。
4. 将第一题中的四类延时统一封装，使普通用户态模式和自定义系统调用模式可以切换。
5. 通过独立验证程序和主程序集成运行证明系统调用可用。

### §2.2 第二题原理、方法、过程

#### 2.2.1 内核侧实现思路

本项目采用 4 个系统调用，而不是只定义一个 `diag(number)` 后再由用户态区分操作类型。这样可以清晰对应第一题中的四类耗时操作，便于验收观察。

内核侧新增函数示例：

```c
static long diag_delay_impl(long number, int offset, const char *name)
{
    unsigned int delay_ms = diag_delay_ms(number, offset);
    pr_info("%s(number=%ld) sleep %u ms\n", name, number, delay_ms);
    msleep(delay_ms);
    return 0;
}

SYSCALL_DEFINE1(diag_read, long, number)
{
    return diag_delay_impl(number, 1, "diag_read");
}
```

`diag_load`、`diag_write`、`diag_refresh` 与 `diag_read` 类似，只是 offset 和日志名称不同。由于学号 `20241001655` 超过 32 位 `int` 范围，因此内核侧参数建议使用 `long number`，用户态使用 `long long student_no`。

#### 2.2.2 内核修改步骤

在普通 Ubuntu 虚拟机或 WSL2 Ubuntu 自定义内核中，步骤如下：

1. 准备 Linux 内核源码和编译依赖。
2. 新增 `kernel/diag.c`，实现 `diag_read`、`diag_load`、`diag_write`、`diag_refresh`。
3. 在 `kernel/Makefile` 中加入 `obj-y += diag.o`。
4. 在 `include/linux/syscalls.h` 中声明四个系统调用。
5. 在 `arch/x86/entry/syscalls/syscall_64.tbl` 中注册系统调用号。
6. 编译并启动新内核。
7. 使用 `uname -r` 确认进入自定义内核。
8. 运行用户态程序，并用 `dmesg | grep diag_` 查看内核日志。

本项目记录的 WSL2 实验调用号如下：

```text

diag_load    = 549
diag_write   = 550
diag_refresh = 551
```

#### 2.2.3 用户态封装

第一题主程序不直接散落调用 `syscall()`，而是统一封装在 `src/delay.cpp` 中：

```text
delay_read(student_no)    -> op_offset = 1
delay_load(student_no)    -> op_offset = 2
delay_write(student_no)   -> op_offset = 3
delay_refresh(student_no) -> op_offset = 4
```

普通构建时，`delay.cpp` 使用 `std::this_thread::sleep_for()` 产生用户态随机延时；系统调用构建时，Makefile 增加：

```text
-DUSE_DIAG_SYSCALL
-D__NR_diag_read=548
-D__NR_diag_load=549
-D__NR_diag_write=550
-D__NR_diag_refresh=551
```

然后 `delay.cpp` 使用：

```cpp
syscall(__NR_diag_read, student_no);
syscall(__NR_diag_load, student_no);
syscall(__NR_diag_write, student_no);
syscall(__NR_diag_refresh, student_no);
```

如果没有进入自定义内核或调用失败，代码保留用户态 fallback，保证第一题仍可运行。

#### 2.2.4 Makefile 支持

题目二相关 Makefile 目标如下：

```text
build-diag      使用系统调用宏重新构建主程序和 user_call_demo
run-diag-demo   单独调用四个 diag 系统调用
run-diag-smoke  使用系统调用延时路径运行小规模主程序
```

如果实验机系统调用号不同，可以覆盖变量：

```bash
make -C OS/library_cache_sync build-diag \
  DIAG_NR_READ=<nr1> DIAG_NR_LOAD=<nr2> \
  DIAG_NR_WRITE=<nr3> DIAG_NR_REFRESH=<nr4>
```

### §2.4 第二题出现的错误及解决方法

1. 问题：学号 `20241001655` 超过 32 位 `int` 范围，如果内核侧使用 `int number`，会导致学号截断。
   解决方法：用户态使用 `long long student_no`，内核侧系统调用参数使用 `long number`。

2. 问题：普通开发环境没有注册新的系统调用号，直接运行系统调用版本可能返回 `ENOSYS`。
   解决方法：`delay.cpp` 中保留 fallback；如果系统调用失败，则退回用户态延时，保证第一题功能仍可运行。真正验收时需进入已注册系统调用的新内核。

3. 问题：系统调用号和内核版本相关，不同实验机可能不是 548 到 551。
   解决方法：Makefile 把调用号做成变量 `DIAG_NR_READ`、`DIAG_NR_LOAD`、`DIAG_NR_WRITE`、`DIAG_NR_REFRESH`，可在编译时覆盖。

4. 问题：WSL2 不像普通 Ubuntu 一样通过 grub 安装和选择内核。
   解决方法：在 WSL2 中编译 `bzImage` 后，通过 Windows 用户目录下的 `.wslconfig` 指定自定义内核，并用 `wsl --shutdown` 重启。

5. 问题：主程序某一次运行不一定触发缓存刷新，因为写者更新的书未必已经在缓存中。
   解决方法：单独用 `user_call_demo` 验证 `diag_refresh`；主程序用固定 seed 和多轮运行验证写后缓存刷新逻辑。
